# Synthetic data disclosure

`synth/factories_synthetic.json` contains **120 entirely synthetic factories**. No real
company, individual, or facility is represented, referenced, or identifiable in this file.
Every factory name is generated as `"<cluster name> <sector> Unit <NN> (Synthetic)"` and every
record carries `"data_source": "synthetic"`.

This document states, field by field, what in the dataset is real, what is calibrated against
something real, and what is an illustrative placeholder — so nobody downstream (including a
future version of this project) mistakes a plausible number for a verified one. Full citations
are in `sources.md`; this file is the plain-language summary of what that means for each field.

## Field-by-field provenance

| Field | Status | Basis |
|---|---|---|
| Cluster id, name, district | **Real** | Known GIDC industrial clusters — see `sources.md` #5 |
| Cluster lat/lon | **Calibrated** | Approximate town/cluster centroid, ±a few km, not surveyed |
| Factory id, name, exact lat/lon, monthly time series | **Synthetic** | Generated by `scripts/generate_synthetic.py`, seed 42, fully reproducible |
| Emission factors (fuel → kgCO2e) | **Real** | CEA v19.0, IPCC 2006 Table 1.4/2.2 — see `sources.md` #1-2 |
| Process benchmark intensity — Textiles | **Real** | BEE PAT Cycle-1 (Textiles was an original PAT sector) — see `sources.md` #4 |
| Process benchmark intensity — Ceramics, Chemicals, Engineering | **Documented estimate, medium confidence** | Cleaner-production audit literature; explicitly NOT BEE PAT (those sectors were outside PAT Cycle-1 scope) — see `sources.md` #4 and `LIMITATIONS.md` #4 |
| Hazardous/general waste ratios per sector | **Calibrated** | Anchored to CPCB 2019-20 Gujarat state total (24.85 lakh t/yr), sector split is a documented judgement call, not a cited breakdown — see `sources.md` #3 and `LIMITATIONS.md` #3 |
| Factory output-scale ranges (t/yr) | **Illustrative / is_placeholder** | Order-of-magnitude judgement call, not independently sourced — see `LIMITATIONS.md` #7 |
| Fuel-mix-per-process-kind assumptions | **Calibrated** | Defensible typical mix (e.g. kilns run mostly natural gas + some pet coke), not a cited figure |
| Per-factory/per-process performance ratio (how far a factory runs from benchmark) — Ceramics, Textiles | **Real CV, synthetic draw** | Spread (coefficient of variation) is computed from real BEE/SAMEEEKSHA cluster-manual Specific Energy Consumption range tables (Morbi ceramic cluster, Surat textile cluster); the individual per-factory *draw* from that real-CV Gaussian is still synthetic — see `LIMITATIONS.md` #10 |
| Per-factory/per-process performance ratio — Chemicals, Engineering | **Synthetic, by design** | No output-normalised SEC-range table located for these sectors in this research pass; kept at the original unsourced CV (≈0.116) rather than borrowing another sector's real number — see `LIMITATIONS.md` #10 |
| Month-to-month noise within one factory (all sectors) | **Partially sourced, partially assumed** | Ceramics/Textiles: derived as a disclosed 0.5× fraction of the sourced cross-sectional CV above (the 0.5× ratio itself is not sourced — no public month-by-month SEC series for individual Indian MSME units was found). Chemicals/Engineering: unchanged from the original unsourced range. See `LIMITATIONS.md` #10 |
| Injected anomalous months | **Synthetic, labelled separately** | Count varies slightly with generator changes (currently 26 months across 20 factories of 120), multiplier 1.4–2.1×, labels held in `synth/anomaly_ground_truth.json` only — never exposed to the model-facing dataset, so a future anomaly detector can be scored against real ground truth |
| Alang (ship-recycling) process template | **Reused, documented simplification** | No dedicated ship-recycling process template exists in this dataset; Alang factories are generated using the Engineering template (furnace/cutting, compressor, heat-treat) as a stated approximation, not a fabricated new sector |
| Waste-stream tag catalog (`clean/waste_stream_profiles.csv`) | **Real category names, calibrated quantities** | Category *names* widened from real waste-characterization literature (ceramic cutting/polishing sludge as distinct from ETP sludge; textile lime/salt sludge distinct from bio sludge; chemical spent catalyst; foundry baghouse/grinding dust) — see the CSV's own `source` column per row for citations. The `share_of_basis` tonnage ratios remain a documented modelling estimate, not an individually cited ratio (same convention as the pre-existing rows) |

## What this dataset is FOR

- Giving the Phase-2/3 database and ML layers something structurally realistic to run
  against, calibrated to the real sourced figures above wherever a real figure exists.
- Producing genuine benchmark-deviation spread (via the performance-ratio mechanism) so
  hotspot ranking, root-cause diagnosis, and the anomaly detector have real signal to find —
  not hand-authored "this factory looks bad" numbers.
- Giving the anomaly detector a labelled evaluation set (`anomaly_ground_truth.json`) so its
  eventual precision/recall figures are measured, not asserted.

## What this dataset is NOT

- Not a claim that these are real Gujarat factories, real emissions, or real waste figures
  for any specific site.
- Not a substitute for the ASI Gujarat SME micro-data this project was unable to obtain (see
  `LIMITATIONS.md` #1) — it is a calibrated stand-in, disclosed as such everywhere it
  surfaces in the product.
- Not pre-computed diagnosis output — see `LIMITATIONS.md` #5. The engine (Phase 2) must
  compute CO2e, benchmark deviation, severity, and recommendations from this raw activity
  data; nothing here should be copied into the product as a finished answer.

## Regenerating this dataset

```
cd data-pipeline
python scripts/generate_synthetic.py
python scripts/validate.py
```

Both scripts are deterministic (fixed `RANDOM_SEED = 42` in `generate_synthetic.py`);
re-running produces byte-identical output. If you change the generation logic in a way that
should produce a genuinely new dataset version, bump `SCHEMA_VERSION` in
`generate_synthetic.py` so downstream consumers (Phase 2 DB seed loader) can detect the
change.
